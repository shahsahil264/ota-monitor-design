UpgradeBlocker + Upgrades — ADDITIVE. Stay forever. Never removed.

Lifecycle labels — MUTUALLY EXCLUSIVE. ADD next first, REMOVE previous (crash-safe).

Priority (first match wins): UpdateRecBlocked > ISProposed > ISRequested > UpgradeBlocker only

Idempotency (3 layers): linked issues (primary) > bot comments (fast) > labels (tertiary)

Four Skills

Skill 1: Monitor 9am + 3pm

Three-pass filtering: query_jira (cheap) → filter by labels → get_jira_issue on candidates only. 10 detection rules with short-circuit (STOP at first match). Pipeline FAILED check (best-effort). Heartbeat every run.

Skill 2: Lifecycle Button-driven

4 gates + auto-actions. Stale-button check on every click. OrgData for project routing. Resume checklist for crash recovery. Multi-turn execution (3 turns for Gate 2).

Skill 3: PR Generator Workspace

5 phases: setup (fork) → generate (/propose-risk) → PR (approval-gated) → monitor (event/scan) → post-merge (labels + close Spike). Branch: blocked-edges/OCPBUGS-X-{action}

Skill 4: Handover Friday 4pm

Two phases: gather from 9 sources (compact every 3) → synthesize HTML. Deterministic data only. Cross-check counts. Never empty handover.

Prompt Files

These 4 markdown files are delivered to the Chai Bot team. They define the persona's behavior. Click to expand.

01_role.md Persona Identity

▶
State machine, idempotency rules, button definitions, impact statement template, Spike creation details, stale-button check, error handling, bounds. Key rules: • UpgradeBlocker + Upgrades labels stay forever (additive) • Lifecycle labels are mutually exclusive (ADD first, REMOVE second) • 3-layer idempotency: linked issues > bot comments > labels • Always Spike URL for blocked-edge url field, never OCPBUGS • Re-read bug state on every button click (stale-button check) • Max 50 bugs/run, max 10 alerts, max 3 retries, max 1 PR per risk • Bot-created orphaned Spikes auto-close. Human-created: alert only. • Corrections via conversation (no button)

monitor-enriched.md 9am Task

▶
8-step pipeline. Runs every weekday at 9am ET. Always posts. Step 1: Two JQL queries (primary: active bugs, secondary: fixedIn candidates) Step 2: Filter by labels — only inspect bugs that MIGHT need action Step 3: get_jira_issue on candidates only (batches of 10, compact between) Step 4: 10 detection rules (STOP at first match, NEXT BUG): Rule 1: fixedIn available → [Add FixedIn] Rule 2: Active blocker → count only Rule 3: Spike in Code Review → AUTO-TRANSITION (fall-through to Rule 4) Rule 4: Impact ready → [Accept—Block Edge] / [Revise] / [Not a Blocker] Rule 4b: Review reminder (24h) Rule 5: Stale request (48h) → team tagged via OrgData Rule 5b: Escalation (7d) Rule 6: New UpgradeBlocker → duplicate check → [Create Spike] Rule 6b: Already offered → skip Orphaned: auto-close bot-created Spikes, alert for human-created Step 5: Pipeline check (best-effort Slack search for FAILEDs) Step 6: Batch >3 new bugs → summary table Step 7: Daily status (always post) Step 8: Error reporting

monitor-brief.md 3pm Task

▶
Same Steps 1-6 as enriched. Differences: • NO daily status section (if composing one, STOP) • Silent if nothing changed (heartbeat to thread only) • Posts top-level ONLY for: new bug, impact ready, fixedIn, stale, FAILED, orphan, or error

weekly-handover.md Friday Task

▶
Two phases. Runs Friday 4pm ET. Always posts. PHASE 1 — Data gathering (compact every 3 sources): Source 1: Active blockers by stage (JQL) Source 2: Items waiting on teams Source 3: Resolved this week (JQL) Source 4: Open PRs (GitHub API) Source 5: Merged PRs this week (GitHub API) Source 6: Pipeline health (indexed Slack, including stale Recommend waiting >14d) Source 7: Bot activity metrics ([OTA-Monitor] comment counts) Source 8: Feedback signals (OTA-MONITOR-FEEDBACK ticket) Source 9: Latency metric (approximate: Spike offered timestamp − bug updated) PHASE 2 — Synthesis: HTML artifact via send_html_to_thread Sections: Immediate Attention, Blockers by Stage, Waiting on Teams, Waiting on OTA, Resolved, PRs, Pipeline, Bot Performance, Key Contacts, Notes for Incoming Monitor Verification: output count == JQL count Error: [DATA UNAVAILABLE] markers, never empty handover
